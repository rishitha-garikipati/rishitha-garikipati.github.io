Version notes (late 2026)

  • Java: learn on Java 21 LTS (most widely used in companies). Know what's new in Java 25 LTS. Many companies still run Java 8/11/17, so know the differences.
  • Spring Boot: most jobs use 3.x; 4.x (Spring Framework 7) is the newest. The concepts are the same. Learn on 3.x/4.x, never 2.x tutorials (they use the old javax.* package names; new code uses jakarta.*).
  • React: React 19 with Vite. Create React App is deprecated, so skip tutorials that use it.
  • Kafka: Kafka 4.x runs in KRaft mode (ZooKeeper has been removed). Older tutorials with ZooKeeper are fine for concepts only.

⭐ ShopSphere: a full e-commerce platform

What it is: an online store like a small Amazon/Flipkart. Customers browse products, search, add to cart, check out and track orders. Admins manage products, stock, orders and see sales dashboards. There's also a flash-sale feature, where thousands of users try to buy limited stock at the same time.

Why this project: everyone understands e-commerce. It naturally needs every skill in this guide (data modelling, concurrency, security, events, scaling), and it matches the most common microservices and system design interview questions.

Final architecture: React storefront + React admin panel → API Gateway → 9 Spring Boot microservices (auth/user, catalog, search, cart, order, inventory, payment-mock, review, notification) → PostgreSQL, Redis, Kafka, OpenSearch → running in Docker/Kubernetes, deployed with CI/CD and monitored with Prometheus + Grafana + tracing.

Build plan: 7 phases matched to the roadmap

Each phase ends with a working, tested, committed version and a short LinkedIn post. Never break what already works; tag a release (v0.1, v0.2…) at the end of each phase.
Phase 0 (weeks 1–6): shopsphere-core, pure JavaCore Java · Advanced Java · DSA
  • Plain Java + Maven library, no Spring: Product, Category, Cart, Order, Customer, Coupon domain classes.
  • Pricing engine: taxes, coupons, discount rules with the Strategy pattern, all in BigDecimal.
  • CSV product importer with validation and an error report.
  • Trie autocomplete, LRU "recently viewed", top-K bestsellers with a heap.
  • Concurrency: simulate 1,000 threads buying 50 units of a flash-sale item, show the race condition, then fix it (synchronized → locks → atomics) and compare.
  • JUnit 5 tests for everything. Done when: 80%+ coverage, a clean README, published on GitHub.
Phase 1 (weeks 7–10): Spring Boot monolith backendSpring · SQL · Security · Testing
  • Reuse the Phase 0 domain inside a Spring Boot app with a modular package structure (catalog, cart, order, user).
  • PostgreSQL schema + Flyway; JPA entities and relationships; Specifications for search, filters and pagination.
  • REST APIs, validation, ProblemDetail errors, MapStruct DTOs, OpenAPI docs.
  • JWT auth with CUSTOMER/ADMIN roles; Redis cache for the catalogue; @Scheduled abandoned-cart job; Spring Batch product import.
  • Admin SQL reports with window functions; tune indexes with EXPLAIN ANALYZE.
  • Done when: unit + slice + Testcontainers tests pass and Swagger shows every endpoint.
Phase 2 (weeks 11–13): React storefront + admin, deploy v1React · TypeScript · DevOps basics
  • Storefront: home, catalogue with filters, search with autocomplete, product page, cart, checkout, order history.
  • Admin: product CRUD with image upload, order list and status updates, sales charts.
  • TanStack Query, Zustand cart, React Hook Form + Zod, protected routes, lazy loading, Vitest + RTL tests.
  • Docker Compose for the whole stack; deploy (backend on Render/Railway/AWS, frontend on Vercel/Netlify).
  • Done when: live demo link works end to end. Start applying for jobs now.
Phase 3 (weeks 14–15): split into microservicesMicroservices
  • Extract user, catalog, cart, order, inventory, payment-mock, review and notification services, each with its own database.
  • Spring Cloud Gateway, service discovery, centralised config; Keycloak for OAuth2/OIDC login.
  • Synchronous calls with RestClient/OpenFeign + Resilience4j (timeouts, retries, circuit breaker, fallbacks).
  • Write ADRs explaining why and how you split it.
  • Done when: the React app works unchanged through the gateway.
Phase 4 (weeks 16–17): event-driven with KafkaKafka · Saga · Outbox
  • Checkout Saga over Kafka: OrderCreated → StockReserved → PaymentCompleted → OrderConfirmed, with compensation on failure (the payment mock fails ~20% of the time).
  • Transactional outbox (+ Debezium); idempotent consumers; retry topics and a dead-letter topic with a re-process admin endpoint.
  • notification-service emails customers; WebSocket pushes live order status to React.
  • search-service: Debezium CDC → Kafka → OpenSearch for full-text product search.
  • Clickstream → Kafka Streams → "Trending now" widget on the home page.
  • Done when: killing any one service mid-checkout never leaves stock or orders in a wrong state.
Phase 5 (weeks 18–20): production setupDocker · Kubernetes · CI/CD · Cloud · Observability
  • Kubernetes manifests/Helm with probes, ConfigMaps, Secrets, autoscaling; run on kind/minikube.
  • GitHub Actions: PR checks (tests, JaCoCo, Sonar), images pushed to a registry on merge, automatic deploy.
  • Prometheus metrics, Grafana dashboards (orders/min, error rate, consumer lag), OpenTelemetry traces across services.
  • Cloud deployment on AWS (stay on the free tier) or a cheaper alternative, documented step by step.
  • Done when: a push to main reaches a running environment automatically and you can trace one checkout across all services.
Phase 6 (weeks 21–24): harden, measure and presentTesting · System Design · SE Practices
  • Flash-sale load test with Gatling (e.g. 5,000 users, 100 units): prove there's no overselling; try Redis atomic counters vs DB locking and record the numbers.
  • Playwright end-to-end checkout test in CI.
  • Security pass against the OWASP Top 10; dependency scanning.
  • Inject an incident (e.g. Kafka consumer stuck), handle it, write a blameless postmortem.
  • Final design doc + architecture diagrams + a 3–5 minute demo video + a polished README.
  • Done when: you can whiteboard the whole system and explain every trade-off in 10 minutes.

Are there roles for your experience? Yes.

Java + Spring Boot + React is one of the most hired-for stacks in India, across product companies, global capability centres (GCCs), IT services and startups. With about 1 year of total experience (6 months full-time + 6 months internship), you fit 0–2 year and 1–3 year openings, as well as associate and graduate programs.

Be honest about experience: write "1 year (including a 6-month internship)" or list them separately. Many recruiters count only full-time months; don't stretch it. Your projects make up the difference.

Where to target

A. Internal move (fastest route)

Ask your current manager or HR whether you can transfer to a development team inside the company. Meanwhile, volunteer for any scripting, SQL tooling, automation or API work. That gives you real development experience to put on your resume.

B. Product companies and global capability centres (GCCs)

India has thousands of engineering centres of global companies (retail, e-commerce, SaaS, travel, telecom, healthcare, manufacturing and more), and many run Java/Spring backends with React frontends. Search LinkedIn for "Java Spring Boot React" filtered by 0–2 years, and check career pages of companies whose products you use.

C. IT services and consulting (high volume, easier entry)

TCS, Infosys, Wipro, HCLTech, Cognizant, Accenture, Capgemini, LTIMindtree, Tech Mahindra, Virtusa, Hexaware. They hire Java full stack developers in large numbers, and moving between projects later is common.

D. Startups (fast learning, broad ownership)

Use Wellfound, Cutshort and Instahyre. Check the tech stack in every post (some use Node/Go/Python). Expect DSA + machine-coding rounds and a deep discussion of your projects.

How to talk about the switch in interviews

The core frame: "I'm not running away from my current role. I'm moving toward building software." Every answer should go Past (what I learned) → Present (what I've built to prove it) → Future (why this role).

Principles

✅ Do

  • Link your current skills to engineering: SQL, working with data, troubleshooting, production support, following processes.
  • Back every claim with evidence: projects, GitHub, anything you automated.
  • Sound sure: "I made a deliberate decision", not "I thought maybe I'd try".
  • Keep the switch explanation under 60–90 seconds, then steer to your projects.
  • Show you've started already (months of consistent learning and building).

❌ Don't

  • Criticise the current company, team, manager or the tool.
  • Say your current work is "boring" or "I'm not learning anything".
  • Make it sound like it's only about money.
  • Apologise for your background; it gave you useful skills.
  • Claim experience you don't have. Projects are projects; label them honestly.

"Tell me about yourself" (60–90 seconds)

I'm [Name]. I have about a year of experience, first as an intern and then full-time, working on a data reconciliation platform (IntelliMatch), where I [configured data-processing rules / investigated data issues with SQL / supported daily production runs]. That gave me solid SQL skills and a habit of being careful about data quality and edge cases.

Working with these systems every day, I realised the part I enjoyed most was understanding how software is built and automating things, so over the last [N] months I've been seriously building my skills in Java, Spring Boot, React and Kafka. I've built ShopSphere, an e-commerce platform that started as a Spring Boot monolith and grew into microservices with Kafka-based order processing, a React storefront, and Docker, Kubernetes and CI/CD.

I'm now looking for a Java full stack role where I can build and own features end to end and keep growing as an engineer.

"Why are you switching to development?"

In my current role I work with an existing product: configuring it, running it and fixing data issues. Over time I became more interested in how such systems are designed and built than in operating them. When I started writing SQL and small automations, I found I enjoyed the building part most. So I made a deliberate plan: I learned Java and Spring Boot properly and built real projects to make sure this is what I want, and it is. Development lets me create things and solve problems at the root.

"Why switch so early in your career?"

Because early is the best time to do it. The first few years set your technical foundation, and I'd rather build mine as an engineer now than switch after 5 years, when it's much harder and costlier for both me and an employer. I'm not starting from zero either: a year in a professional IT environment taught me SQL, production discipline, working with deadlines and teams. Getting clarity early is an advantage, not a risk.

"You have no professional development experience. Why should we hire you?"

That's fair. I haven't been a developer by title yet. What I can show is (1) projects that go beyond tutorials, using the same stack your team uses: Spring Boot, React, Kafka, microservices and tests; (2) a year of professional experience, so I know how real teams, processes and production systems work; and (3) proof I learn fast and consistently, since I built all this while working full-time. I'd be happy to walk you through any part of my code.

"Isn't this a step back for you?" / "Will you accept a junior role?"

I see it as a step forward in direction. I'm comfortable starting at an associate or SDE-1 level, because the role and the learning matter more to me right now than the title. My professional experience should help me ramp up faster once I'm in.

"You've only been in your current job about 6 months. Will you leave us quickly too?"

This move is the opposite of job-hopping. I'm switching career tracks, not hopping between similar jobs. I took my time to be sure, spent months building skills and projects, and I'm choosing a role I want to grow in for the long term. My plan is to go deep as an engineer here.

"What from your current role helps you as a developer?"

  • SQL depth: joins, aggregations and finding missing or mismatched records across large datasets.
  • Data quality mindset: small data errors cause big problems, so I code defensively and validate inputs.
  • Edge-case thinking: duplicates, partial data, timing issues, bad input files.
  • Production mindset: SLAs, incident handling, root-cause analysis, clear communication during issues.
  • Teamwork & process: working with other teams, tickets, deadlines and documentation.

"How do you know you'll enjoy development?"

I tested it before deciding. I built ShopSphere step by step from a plain Java library to a deployed microservices platform, including the hard parts: debugging Kafka consumers, handling concurrent orders without overselling, writing tests and setting up Docker and CI. I enjoyed even the frustrating parts, and I kept going consistently for [N] months alongside a full-time job. That's what convinced me.

Questions to ask the interviewer

  • How are code reviews and mentoring done for junior engineers?

Salary and notice period answers

  • Expected CTC: "Based on my research for this role and my experience, I'm looking at a range of X–Y. I'm flexible for the right learning opportunity." (Research the range first.)
  • Notice period: state it plainly, and mention whether it can be bought out or shortened.
  • Current CTC: answer honestly. Don't inflate it; it gets checked against payslips.
